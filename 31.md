# NUT-31: Mint and melt fees

`optional`

`depends on: NUT-04 NUT-05 NUT-06 NUT-23`

---

This document defines two mint-charged fees for the value-carrying operations
that cross the mint boundary:

| Direction | Operation | Fee |
|---|---|---|
| in | mint (pay-in) | `mint_fee` |
| out | melt (payout) | `melt_fee` |

Both are a proportion of the operation `amount`, kept by the mint. They are the
in/out counterparts of the existing within-mint swap fee ([NUT-02][02]
`input_fee_ppk`), which is **out of scope** here and unchanged.

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT" and "MAY" are to be
interpreted as described in RFC 2119.

## Rationale

- **Why amount-based, not per-input.** The [NUT-02][02] swap fee is per input
  because the mint's cost to verify and store a proof is independent of its
  value. A mint's cost to pay in or out, by contrast, scales with the amount
  (Lightning routing, onchain miner fees, liquidity), so `mint_fee`/`melt_fee`
  are a proportion of `amount`. A per-input fee would also be non-monotonic in
  the amount (a large payout made of few proofs could cost less than a small one
  made of many), which is undesirable for a payout price.
- **Why kept, not taken from the reserve.** The [NUT-05][05] `fee_reserve` is a
  refundable routing budget returned to the wallet as change ([NUT-08][08]). A
  fee under this NUT is a price the mint keeps; charging it on top of, rather
  than out of, the reserve keeps the quoted `fee_reserve` the wallet's true
  refundable budget and keeps the two amounts independently auditable.
- **Why per `(method, unit)`.** The mint's real cost differs by rail: an
  `onchain` ([NUT-30][30]) melt costs a variable miner fee, so its `melt_fee`
  will typically exceed a `bolt11` ([NUT-23][23]) payout, while an `onchain`
  mint (deposit) may be free. Rates are therefore set per `(method, unit)`, the
  same scope [NUT-04][04]/[NUT-05][05] already use for `min_amount`/`max_amount`.
- **Why basis points.** A single integer unit (`1 bps = 0.01%`) for both fees is
  simple to reason about and, unlike a percentage, needs no floating point.

## Rate unit

Both rates are expressed in **basis points (bps)** of the operation `amount`,
denominated in the method's `unit`. `1 bps = 0.01%`, `100 bps = 1%`,
`10000 bps = 100%`. The fee amount is rounded **up**:

```python
def fee(amount: int, bps: int) -> int:
    return (amount * bps + 9999) // 10000   # ceil(amount * bps / 10000)
```

Integer arithmetic only; floating point **MUST NOT** be used, to keep the result
deterministic across implementations.

`fee_bps` **MUST** be a non-negative integer. A mint **SHOULD NOT** advertise
`fee_bps > 10000` (a fee exceeding 100% of the amount). Because the fee rounds
up, a nonzero rate on a very small amount yields at least `1` unit of fee (e.g.
`amount = 1, fee_bps = 1 → fee = 1`). A rate of `0`, or an absent advertisement,
means the fee is not charged and this NUT is a no-op for that `(method, unit)`.

## Advertisement (NUT-06)

A mint advertises its rates per `(method, unit)` in the [NUT-06][06]
`GetInfoResponse.nuts` object, inside the `options` of the existing
`MintMethodSetting` / `MeltMethodSetting` entries (the same `options` slot
[NUT-23][23] uses for `description` and `amountless`):

```json
"4": {
  "methods": [
    { "method": "bolt11",  "unit": "sat", "options": { "fee_bps": 0 } },
    { "method": "onchain", "unit": "sat", "options": { "fee_bps": 0 } }
  ],
  "disabled": false
},
"5": {
  "methods": [
    { "method": "bolt11",  "unit": "sat", "options": { "fee_bps": 100 } },
    { "method": "onchain", "unit": "sat", "options": { "fee_bps": 300 } }
  ],
  "disabled": false
}
```

Each `(method, unit)` carries its own `fee_bps`; the example charges nothing to
mint, 1% to melt over Lightning, and 3% to withdraw onchain. A mint MAY also
advertise `"31": { "supported": true }`.

The advertised rate is a **discovery hint**. The **binding** price for a specific
operation is the absolute `mint_fee` / `melt_fee` returned in the quote (below).
A mint **MUST** honor the fee quoted for a given quote and **MUST NOT** change it
after the quote has been issued, even if it later changes its advertised
`fee_bps`.

## Mint fee (pay-in)

Extends the mint flow of [NUT-04][04] / [NUT-23][23]. When the mint charges a
mint fee, the payment `request` collects `amount + mint_fee`, but only `amount`
worth of ecash is mintable; the mint keeps `mint_fee`. The
`PostMintQuoteBolt11Response` gains a `mint_fee` field (in `unit`):

```json
{
  "quote": <str>, "request": <str>, "amount": <int>, "mint_fee": <int>,
  "unit": <str_enum[UNIT]>, "method": "bolt11",
  "amount_paid": <int>, "amount_issued": <int>, "updated_at": <int>,
  "expiry": <int|null>
}
```

- `mint_fee = ceil(amount * fee_bps / 10000)`, fixed for the quote.
- `amount` is the mintable ecash (unchanged meaning). For `bolt11`, the invoice
  `request` is for `amount + mint_fee`.
- `amount_paid` keeps its [NUT-04][04] meaning — the total that has been paid to
  the mint for this quote (so a fully paid `bolt11` quote has
  `amount_paid = amount + mint_fee`). NUT-31 modifies only the mintable rule:
  when `mint_fee > 0`, the amount currently mintable is

  ```
  mintable = max(0, amount_paid - mint_fee - amount_issued)
  ```

  and the mint **MUST NOT** sign outputs whose total exceeds `mintable`. This
  deducts the fee from the accrued paid total, so it also composes with the
  multi-payment / top-up flow of [NUT-04][04] (the fee is taken from the first
  credited units; nothing is mintable until `amount_paid > mint_fee`). For a
  single full `bolt11` payment this reduces to `mintable = amount`.

**Example** (`fee_bps = 100`, i.e. 1%): request `amount = 1000 sat` →
`mint_fee = 10`, invoice for `1010 sat`. After payment `amount_paid = 1010`;
`mintable = 1010 - 10 - 0 = 1000`; the wallet mints `1000 sat`; the mint keeps
`10 sat`.

> [!WARNING]
> **`mint_fee` REQUIRES wallet awareness.** A wallet that does not implement
> this NUT quotes `amount`, receives an invoice for `amount + mint_fee`, pays it,
> and then can mint only `amount` — it has overpaid by `mint_fee` with no way to
> account for it, which surfaces to the user as a loss. Unlike `melt_fee` (which
> fails cleanly *before* payment, see below), a non-zero `mint_fee` against an
> unaware wallet causes user-visible overpayment. A mint therefore **MUST NOT**
> enable a non-zero `mint_fee` for a `(method, unit)` unless the wallets it
> serves implement this NUT.

## Melt fee (payout)

Extends the melt flow of [NUT-05][05] / [NUT-23][23]. The
`PostMeltQuoteBolt11Response` gains a `melt_fee` field alongside `fee_reserve`:

```json
{
  "quote": <str>, "request": <str>, "amount": <int>,
  "fee_reserve": <int>, "melt_fee": <int>,
  "unit": <str_enum[UNIT]>, "method": "bolt11",
  "state": <str_enum[STATE]>, "expiry": <int>, "payment_preimage": <str|null>
}
```

- `melt_fee = ceil(amount * fee_bps / 10000)`, fixed for the quote, kept by the
  mint when the payment succeeds.
- The balance the mint enforces at melt time becomes:

  ```
  sum(inputs) >= amount + fee_reserve + melt_fee + input_fee
  ```

  where `input_fee` is the [NUT-02][02] swap fee for the provided inputs. A mint
  **MUST** reject an under-funded melt (error `11005`, see [NUT-05][05]).
- `fee_reserve` remains refundable via [NUT-08][08]; `melt_fee` is **excluded**
  from the change calculation (deducted before it), so [NUT-08][08] is unchanged
  in shape and still returns only unused routing reserve.
- `melt_fee` is always denominated in `unit` (never msat), even when the melt
  quote request supplies its amount in msat (MPP, [NUT-15][15]; amountless,
  [NUT-23][23]).

**Example** (`fee_bps = 100`): a `bolt11` invoice `amount = 1000 sat`,
`fee_reserve = 10`, `input_fee = 0` → `melt_fee = 10`; the wallet funds
`>= 1020 sat`. If routing costs `2 sat`, the mint keeps `melt_fee = 10` and
returns `fee_reserve - 2 = 8 sat` as change. `melt_fee` never comes out of the
reserve.

## Wallet flow

A wallet that implements this NUT:

- **Mint.** MUST read `mint_fee` from the mint quote, MUST expect the payment
  `request` to collect `amount + mint_fee`, and MUST construct outputs whose
  total equals `amount` (never `amount + mint_fee`). It SHOULD display
  `mint_fee` as the mint's fee.
- **Melt.** MUST read `melt_fee` from the melt quote and MUST provide inputs with
  `sum(inputs) >= amount + fee_reserve + melt_fee + input_fee`. It SHOULD display
  `melt_fee` distinctly from the refundable `fee_reserve`.
- **Both.** SHOULD refuse to proceed if the quoted fee exceeds what the user
  agreed to, and SHOULD warn if `mint_fee`/`melt_fee >= amount`.

The GET mint-quote and GET melt-quote endpoints ([NUT-04][04]/[NUT-05][05])
return the same response structures and therefore also echo `mint_fee` /
`melt_fee`.

## Errors

NUT-31 introduces no new error codes; it reuses those of [NUT-05][05] (see
`error_codes.md`):

- An under-funded melt (`sum(inputs) < amount + fee_reserve + melt_fee +
  input_fee`) is rejected as `11005` "Transaction is not balanced".
- A mint request whose outputs exceed `mintable` (above) violates the
  [NUT-04][04] mintable invariant and is rejected the same way NUT-04 rejects
  over-issuance.

The `31xxx` error range is used by [NUT-22][22]; NUT-31 MUST NOT define codes in
it.

## Edge cases

- **Internal settlement** (a melt settled against a mint quote of the same mint,
  no routing): fee-free (`melt_fee = 0`), consistent with `fee_reserve = 0`.
- **Partial (MPP) payments** ([NUT-15][15]): `melt_fee` is computed on the
  quote's `amount` (the partial amount), once per quote, kept once — never per
  shard.
- **Amountless invoices** ([NUT-23][23]): `melt_fee` is computed on the
  wallet-supplied amount.
- **Fee ≥ amount**: possible for a very high `fee_bps` or a tiny `amount`; the
  mint returns it in the quote and the wallet SHOULD warn or refuse.

## Interactions

- **[NUT-19][19]** (cached responses): cached mint/melt quote responses carry the
  `mint_fee`/`melt_fee` fields like any other field; no change to NUT-19.
- **[NUT-20][20]** (signed mint quote): unaffected; the fee does not enter the
  quote signature.

## Backwards compatibility

Adding `mint_fee` / `melt_fee` to quote responses and `fee_bps` to method
`options` is additive; a wallet that does not implement this NUT ignores the new
fields. The two fees degrade differently:

- **`melt_fee` degrades safely.** An unaware wallet under-funds and is rejected
  (`11005`) *before* any payment — no funds move.
- **`mint_fee` does not** (see the warning above): an unaware wallet overpays the
  invoice and cannot account for the difference.

A mint therefore SHOULD keep `fee_bps` at `0` until the wallets it serves
implement this NUT, MUST NOT enable a non-zero `mint_fee` against unaware
wallets, and SHOULD advertise its rates so wallets can display the true price.
