# NUT-31: Mint operation fees (mint, swap, melt)

`optional`

`depends on: NUT-02 NUT-04 NUT-05 NUT-06 NUT-23`

---

This document generalizes mint-charged fees to all three ecash operations, using a
single, consistent unit — **parts per thousand (ppk)** — already established for
the swap/input fee in [NUT-02][02]. A mint **MAY** charge:

| Direction | Operation | Fee field | Applies to | Existing? |
|---|---|---|---|---|
| in (`dovnitř`) | mint (pay-in) | `mint_fee_ppk` | the minted `amount` | new (this NUT) |
| within (`uvnitř`) | swap | `input_fee_ppk` | each input `Proof` | [NUT-02][02] |
| out (`ven`) | melt (payout) | `melt_fee_ppk` | the melted `amount` | new (this NUT) |

The swap fee is unchanged; it is listed here only so the three directions form one
coherent model. All three rates are advertised per keyset (see [NUT-02][02] for
`input_fee_ppk`) and, for the mint and melt fees, restated as absolute amounts in
the corresponding quote response so the wallet always knows the price before it
commits.

A fee charged under this NUT is **kept by the mint**. It is distinct from the
Lightning `fee_reserve` of [NUT-05][05], which is a refundable routing budget
returned to the wallet as change via [NUT-08][08]. A mint that implements this NUT
**MUST NOT** fold a kept fee into the `fee_reserve`.

## Rate unit

All three rates use the **parts-per-thousand (ppk)** unit of [NUT-02][02] and are
denominated in the keyset's `unit`. A rate of `0`, `null`, or an omitted field
means the fee is not charged. Every fee amount is rounded **up** to the next
integer of the unit:

```python
def ceil_div(numerator: int, denominator: int) -> int:
    return (numerator + denominator - 1) // denominator
```

Floating-point division **MUST NOT** be used, to keep the result deterministic
across implementations.

- **Swap (input) fee** — per input, as in [NUT-02][02]:
  `fee = ceil( sum(input_fee_ppk of each input) / 1000 )`.
- **Mint fee** — on the minted amount:
  `mint_fee = ceil( amount * mint_fee_ppk / 1000 )`.
- **Melt fee** — on the melted amount:
  `melt_fee = ceil( amount * melt_fee_ppk / 1000 )`.

The swap fee is per-input because the mint's cost per proof is independent of the
proof's value ([NUT-02][02]). The mint and melt fees are proportional to the
`amount` because they price the value-carrying operations of issuance and payout.
The unit (ppk) is the same for all three.

## Keyset advertisement

A mint that charges a mint or melt fee **MUST** advertise the rate on the keyset
object returned by `GET /v1/keys`, `GET /v1/keys/{keyset_id}` and
`GET /v1/keysets` (see [NUT-01][01] and [NUT-02][02]), alongside the existing
`input_fee_ppk`:

```json
{
  "id": <hex_str>,
  "unit": <str>,
  "active": <bool>,
  "input_fee_ppk": <int|null>,
  "mint_fee_ppk": <int|null>,
  "melt_fee_ppk": <int|null>,
  "final_expiry": <int|null>
}
```

If `mint_fee_ppk` or `melt_fee_ppk` is not given, the wallet **MUST** assume it to
be `0`.

> [!NOTE]
> Unlike `input_fee_ppk`, the `mint_fee_ppk` and `melt_fee_ppk` rates are **not**
> part of the keyset `id` derivation of [NUT-02][02]. They are transaction-time
> prices disclosed in the mint/melt quote (below), which is authoritative, so a
> mint can change them without rotating keysets. The keyset field is a discovery
> hint; the quote response is binding for a given quote.

## Mint fee (pay-in)

This extends the mint flow of [NUT-04][04] and, for `bolt11`, [NUT-23][23].

When `mint_fee_ppk > 0` for the requested `unit`, the payment request the mint
returns collects `amount + mint_fee`, but the mint credits only `amount` towards
the mintable balance and keeps `mint_fee`. The `PostMintQuoteBolt11Response` of
[NUT-23][23] gains a `mint_fee` field (denominated in `unit`):

```json
{
  "quote": <str>,
  "request": <str>,
  "amount": <int>,
  "mint_fee": <int>,
  "unit": <str_enum[UNIT]>,
  "method": "bolt11",
  "amount_paid": <int>,
  "amount_issued": <int>,
  "updated_at": <int>,
  "expiry": <int|null>
}
```

- `amount` — the ecash that can be minted (unchanged meaning).
- `mint_fee` — the extra amount the `request` collects on top of `amount`, kept by
  the mint. For `bolt11`, the invoice `request` is for `amount + mint_fee`.
- The mint **MUST** credit only `amount` (not `amount + mint_fee`) to `amount_paid`
  once the request is paid. The mintable balance therefore stays
  `amount_paid - amount_issued`, and the [NUT-04][04] rule
  `sum(outputs) <= amount_paid - amount_issued` is unchanged.

A wallet that does not implement this NUT sees a `request` that is larger than
`amount`. It will still pay it and receive `amount` in ecash; it simply cannot
attribute the difference. Mints **SHOULD** keep `mint_fee_ppk = 0` unless their
wallet ecosystem understands the `mint_fee` field, to avoid surprising users.

### Example

`mint_fee_ppk = 10` (1%), request `amount = 1000 sat`.

```http
POST https://mint.host:3338/v1/mint/quote/bolt11
{ "amount": 1000, "unit": "sat" }
```

```json
{
  "quote": "DSGLX9kevM...",
  "request": "lnbc1010n1...",   // invoice for 1010 sat
  "amount": 1000,
  "mint_fee": 10,
  "unit": "sat",
  "method": "bolt11",
  "amount_paid": 0,
  "amount_issued": 0,
  "updated_at": 1701704757,
  "expiry": 1701704757
}
```

After the 1010 sat invoice is paid, the mint sets `amount_paid = 1000`; the wallet
mints up to `1000 - amount_issued` in ecash. The mint keeps `10 sat`.

## Melt fee (payout)

This extends the melt flow of [NUT-05][05] and, for `bolt11`, [NUT-23][23].

When `melt_fee_ppk > 0`, the melt quote gains a `melt_fee` field (denominated in
`unit`) alongside the refundable `fee_reserve`:

```json
{
  "quote": <str>,
  "request": <str>,
  "amount": <int>,
  "fee_reserve": <int>,
  "melt_fee": <int>,
  "unit": <str_enum[UNIT]>,
  "method": "bolt11",
  "state": <str_enum[STATE]>,
  "expiry": <int>,
  "payment_preimage": <str|null>
}
```

The balance the mint enforces at melt time extends the [NUT-05][05]/[NUT-23][23]
rule by the kept `melt_fee`:

```
sum(inputs) >= amount + fee_reserve + melt_fee + swap_input_fee
```

where `swap_input_fee` is the [NUT-02][02] input fee for the provided `inputs`.

- `fee_reserve` — refundable routing budget; unused reserve is returned to the
  wallet as change per [NUT-08][08], exactly as today.
- `melt_fee` — kept by the mint unconditionally when the payment succeeds. It is
  **not** part of the [NUT-08][08] change calculation: the mint deducts it before
  computing overpaid reserve, so the change return of [NUT-08][08] is unchanged in
  shape and still returns only unused `fee_reserve`.

[NUT-08][08] does not need to change: the blank outputs still back only the
refundable `fee_reserve`.

### Example

`melt_fee_ppk = 10` (1%), a `bolt11` invoice for `amount = 1000 sat`,
`fee_reserve = 5 sat`, keyset `input_fee_ppk = 0`.

```json
{
  "quote": "TRmjduhIsP...",
  "request": "lnbc100n1...",
  "amount": 1000,
  "fee_reserve": 5,
  "melt_fee": 10,
  "unit": "sat",
  "method": "bolt11",
  "state": "UNPAID",
  "expiry": 1701704757,
  "payment_preimage": null
}
```

The wallet must provide inputs `>= 1000 + 5 + 10 + 0 = 1015 sat`. If routing costs
`2 sat`, the mint keeps `melt_fee = 10 sat`, and returns `fee_reserve - 2 = 3 sat`
as [NUT-08][08] change. If routing costs the full `5 sat`, the mint still keeps
`10 sat` and returns `0` change. The `melt_fee` never comes out of the reserve.

## Mint info

A mint **MAY** additionally signal support for this NUT in its [NUT-06][06]
`GetInfoResponse.nuts` object:

```json
"31": { "supported": true }
```

The authoritative rates are always the per-keyset fields and the per-quote
`mint_fee` / `melt_fee` values; the [NUT-06][06] flag only advertises that the
mint understands this NUT.

## Edge cases

- **Internal settlement.** When a melt is settled internally against a mint quote
  of the same mint (no Lightning routing), the mint **SHOULD** treat it as
  fee-free (`melt_fee = 0`), consistent with `fee_reserve = 0` for internal
  transfers.
- **Partial (MPP) payments** ([NUT-15][15]). The `melt_fee` is computed on the
  quote's `amount` (the partial amount being paid), once per quote, and kept once.
  It **MUST NOT** be recomputed per shard.
- **Amountless invoices.** For an amountless melt where the amount is supplied by
  the wallet, `melt_fee` is computed on that supplied `amount`.
- **Zero.** A rate of `0`/`null`/absent yields a fee of `0` and this NUT is a
  no-op for that operation.
- **Rounding.** All fees round up (`ceil`), so a nonzero rate on a tiny amount
  yields at least `1` unit of fee.

## Backwards compatibility

Adding `mint_fee` / `melt_fee` fields to quote responses and `mint_fee_ppk` /
`melt_fee_ppk` to keysets is additive. Wallets that do not implement this NUT will
ignore the new fields (see [NUT-01][01] parsing guidance). The failure mode is
that such a wallet under-funds a melt (the mint then rejects it for insufficient
inputs) or cannot attribute a larger-than-`amount` mint invoice. Mints
**SHOULD** therefore keep all new rates at `0` until the wallets they serve
implement this NUT, and **SHOULD** advertise the rates so wallets can display the
true price.
